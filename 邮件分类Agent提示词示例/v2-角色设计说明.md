# 邮件分类系统 Agent 角色设计 v2

## 设计原则

**问题**：过多子代理导致的问题
- Token 消耗随代理数量线性增长
- 并行调用不可控，错误追踪困难
- 协调复杂度高，增加系统不稳定性
- 每个代理都需要独立的 LLM 调用

**解决方案**：按职责整合为4个核心角色

## 精简后的代理架构

```
┌─────────────────────────────────────────────────────────────────┐
│                    Product Agent (产品经理)                      │
│              需求理解 · 任务规划 · 结果整合 · 用户交互             │
└───────────────────────────────┬─────────────────────────────────┘
                                │
            ┌───────────────────┼───────────────────┐
            │                   │                   │
            ▼                   ▼                   ▼
┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
│  Data Agent       │   │  Content Agent    │   │  Backend Agent    │
│  (数据处理专家)    │   │  (内容生成专家)    │   │  (后端开发专家)    │
│                   │   │                   │   │                   │
│  · 邮件分类       │   │  · 摘要生成       │   │  · API设计        │
│  · 信息提取       │   │  · 回复建议       │   │  · 数据库设计     │
│  · 语义检索       │   │  · 内容润色       │   │  · 系统架构       │
│  · 数据清洗       │   │  · 报告生成       │   │  · 性能优化       │
└───────────────────┘   └───────────────────┘   └───────────────────┘
```

## 角色对比

| 维度 | 原方案 (7个代理) | 新方案 (4个代理) |
|-----|-----------------|-----------------|
| **代理数量** | 7个专业代理 | 4个角色代理 |
| **并行复杂度** | 高（7路并行） | 中（最多3路并行） |
| **Token消耗** | 约 7x 基础消耗 | 约 4x 基础消耗 |
| **协调难度** | 高 | 中 |
| **职责边界** | 细粒度，易重叠 | 清晰，互补 |
| **可扩展性** | 新增代理即可 | 新增能力到现有角色 |

## 各角色详细说明

### 1. Product Agent (产品经理)

**职责**：理解用户意图，规划任务，整合结果

| 能力 | 原归属代理 | 说明 |
|-----|-----------|------|
| 需求分析 | Orchestrator | 解析用户请求的真实意图 |
| 任务规划 | Orchestrator | 分解任务，制定执行计划 |
| 代理调度 | Orchestrator | 协调 Data/Content/Backend |
| 结果整合 | Orchestrator | 汇总各代理输出 |
| 统计分析 | Analysis | 生成数据洞察报告 |
| 趋势分析 | Analysis | 识别模式和异常 |

**整合逻辑**：产品经理需要全局视角，分析能力是其决策依据

### 2. Data Agent (数据处理专家)

**职责**：处理所有邮件数据的理解和提取

| 能力 | 原归属代理 | 说明 |
|-----|-----------|------|
| 邮件分类 | Classification | 类别和优先级判断 |
| 信息提取 | Extraction | 实体、行动项提取 |
| 语义检索 | Retrieval | 向量检索、相似度匹配 |
| 数据清洗 | - | 去重、格式化 |

**整合逻辑**：分类、提取、检索都是对数据的"理解"操作

### 3. Content Agent (内容生成专家)

**职责**：生成所有面向用户的文本内容

| 能力 | 原归属代理 | 说明 |
|-----|-----------|------|
| 摘要生成 | Summary | 日报、周报、专题摘要 |
| 回复建议 | Reply | 多选项回复方案 |
| 内容润色 | - | 邮件内容优化 |
| 报告生成 | Summary | 分析报告撰写 |

**整合逻辑**：摘要、回复都是"生成"文本的操作

### 4. Backend Agent (后端开发专家)

**职责**：处理技术实现层面的需求

| 能力 | 说明 |
|-----|------|
| API 设计 | 设计 RESTful 接口 |
| 数据库设计 | 表结构、索引优化 |
| 系统架构 | 模块划分、技术选型 |
| 性能优化 | 缓存、并发处理 |
| 代码生成 | 生成样板代码 |

**新增理由**：开发过程中需要技术实现支持

## 调用流程示例

### 场景1: 新邮件处理

```
用户邮件到达
    │
    ▼
┌─────────────────────────────────────┐
│ Product Agent (理解需求)             │
│ → 识别：新邮件需要分类处理           │
│ → 规划：调用 Data Agent 分类+提取   │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Data Agent (串行处理)               │
│ Step1: 分类 → work_urgent           │
│ Step2: 提取 → 行动项、截止日期       │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Product Agent (整合结果)            │
│ → 返回分类+提取结果                  │
│ → 触发紧急通知（如需要）             │
└─────────────────────────────────────┘
```

**优化点**：原来是 Orchestrator → Classification → Extraction 三个代理串行，现在是 Product → Data 两个代理

### 场景2: 生成每日摘要

```

    │
    ▼
┌─────────────────────────────────────┐

└─────────────────┬───────────────────┘
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
┌───────────────┐   ┌───────────────┐
│ Data Agent    │   │ Content Agent │
│ 获取今日邮件   │   │ (等待数据)     │
│ 检索相关历史   │   │               │
└───────┬───────┘   └───────┬───────┘
        │                   │
        └─────────┬─────────┘

                  │
                  ▼
```

## Token 消耗对比

### 原方案 (单封邮件处理)

| 步骤 | 代理 | 输入 Token | 输出 Token |
|-----|------|-----------|-----------|
| 1 | Orchestrator | 500 | 200 |
| 2 | Classification | 800 | 150 |
| 3 | Extraction | 800 | 300 |
| **总计** | **3次调用** | **2100** | **650** |

### 新方案 (单封邮件处理)

| 步骤 | 代理 | 输入 Token | 输出 Token |
|-----|------|-----------|-----------|
| 1 | Product | 300 | 100 |
| 2 | Data (分类+提取) | 800 | 400 |
| **总计** | **2次调用** | **1100** | **500** |

**节省**：约 48% Token 消耗，减少 33% API 调用

## 错误处理简化

### 原方案

```
Orchestrator → Classification → Extraction
     ↓              ↓              ↓
   失败?          失败?          失败?
     ↓              ↓              ↓
  重试/降级     重试/降级     重试/降级
     ↓              ↓              ↓
     └──────────────┴──────────────┘
                    ↓
              错误传播链长
```

### 新方案

```
Product → Data
   ↓        ↓
 失败?    失败?
   ↓        ↓
 重试     重试
   ↓        ↓
   └────────┘
       ↓
   错误传播链短
```

## 扩展建议

如果后续需要更细粒度控制，可以：

1. **Data Agent 内部分模式**：分类模式、提取模式、检索模式（通过参数控制，不增加代理数量）
2. **Content Agent 内部风格**：正式风格、轻松风格（通过参数控制）
3. **Backend Agent 按技术栈**：Go 后端、Python Agent（通过参数控制）

```python
# 示例：通过模式参数控制 Data Agent 行为
data_agent.execute(
    mode="classify",  # classify | extract | retrieve
    data=email
)
```
